WHAT THEY ARE LEARNING HERE
- LESSON 28: return type annotations (`function f(x: number): number`); why they help (the
  contract, errors reported at the wrong `return`, returned objects keep literal unions);
  `void` (no useful result; returning a value or using the result is an error); "Function
  lacks ending return statement"; honest "may be missing" results such as
  `Account | undefined`; typed destructured parameters; when to annotate returns.
- LESSON 29: optional parameters (`fee?: number`, possibly undefined inside the function)
  and default parameters (`fee = 2.5`, type inferred, never undefined inside); they come after
  required parameters (TS1016); `?` and a default can't be combined (TS1015); only `undefined`
  triggers a default, `null` is reported and would be used as the value; passing `undefined`
  skips a parameter; default for a standard value, `?` when "missing" has its own meaning.
- LESSON 30: function expressions and arrow functions are typed like declarations
  (`(net: number): number =>`); callbacks passed to map/filter/reduce/find get their
  parameter types inferred; standalone arrows need typed parameters; returning an object from
  a short arrow needs `=> ({ ... })`; a `const` arrow can't be used before its declaration.
- LESSON 31: function types (`type FeeRule = (amount: number) => number`) for callback
  parameters, variables and object properties; parameters are inferred from the type; return
  and parameter types must match; fewer parameters fit, more required ones don't; parameter
  names are only labels; `=>`, not `:`, before the return type in a type.
- LESSON 32: type-safe function design (no new syntax) — precise parameter types (literal
  unions, aliases); an options object instead of several optional parameters; honest result
  types such as `{ ok: true; amount: number } | { ok: false; error: ... }` instead of magic
  values like -1; checking outside data once at the edge and passing typed values inward.

MISCONCEPTIONS TO WATCH FOR, IN ORDER OF LIKELIHOOD

1. Deleting a return type to make errors disappear. Ask them where the error shows up next,
   and which line actually contains the mistake.

2. "`void` means the function returns `undefined`, so I can use the result." Ask them what the
   compiler says when they call a method on the result, and what `void` promises callers.

3. Returning a string from a function that should return a line, but printing it instead.
   Ask them what the Verification cell does with the function's result.

4. "Function lacks ending return statement" treated as a bug in TypeScript. Ask them which
   input reaches the end of the function without a `return`.

5. Annotating every tiny helper. Ask them what the annotation adds when the helper is used in
   one place and inference already gets it right.
