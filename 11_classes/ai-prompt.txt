WHAT THEY ARE LEARNING HERE
- LESSON 38: class syntax — property declarations with types at the top of the body, a
  constructor with typed parameters that assigns every property, methods typed like functions;
  strict mode requires every declared property to be assigned (TS2564, "has no initializer and
  is not definitely assigned in the constructor") or to have a starting value; properties are
  reached through `this.` (TS2663 suggests the instance member); the class name is also the
  type of its instances; `new` calls are checked like any other call (TS2554); when a class
  earns its place over a plain object type.
- LESSON 39: access modifiers — `public` (the default), `private` (inside the class body only,
  TS2341), `protected` (the class and its subclasses, TS2445; subclasses themselves come in
  LESSON 43); `private` is per class, so a method may read another instance's private
  property; the modifiers exist only while type checking, so the property is still in the
  object at runtime and `JSON.stringify` prints it; hide first and expose the smallest useful
  surface, keeping the rules inside methods.
- LESSON 40: `readonly` properties (assignable in the declaration and the constructor only,
  TS2540 everywhere else; they lock the property, not the contents of an array it points to —
  `readonly holdings: readonly string[]` is needed for that, and `push` then gives TS2339);
  parameter properties (`constructor(public readonly iban: string, private balance: number) {}`
  declares and assigns in one go; the modifier is what creates the property, so without one
  every `this.x` is reported with TS2339; plain and property parameters can be mixed;
  properties that aren't constructor parameters keep their own declaration with a starting
  value).
- LESSON 41: `static` members belong to the class, reached as `ClassName.member`; three uses —
  `public static readonly` constants, `private static` data shared by all instances (a
  counter), and helpers that need no instance; inside a static method `this` is the class, so
  instance properties give TS2339 on `typeof C`; TS2576 (reached through an instance) and
  TS2662 (class name left out) both name the fix; a counter cannot be `static readonly`
  (TS2540 on the constructor's increment); a class of only static members should be plain
  functions in a module.
- LESSON 42: getters and setters — `get name(): T` is read as `obj.name` with no parentheses,
  `set name(value: T)` runs on assignment; the stored property needs a different name, by
  convention `_name` (sharing it gives TS2300 "Duplicate identifier"); a getter with no setter
  is read-only (TS2540, and the assignment also throws at runtime); getters suit derived values
  worked out on every read, setters suit a rule applied before storing; accessors must stay as
  cheap as a property read; getter for something that reads like data, method for something
  that does work.
- LESSON 43: inheritance — `class B extends A` gives B every property and method of A; the
  derived constructor must call `super(...)` before touching `this` (TS2377, TS17009), and the
  subclass's own parameters, including parameter properties, come after the base ones;
  overriding a method means redeclaring it with a compatible type (TS2416 otherwise);
  `super.method()` calls the base version, so an override can extend instead of replace;
  a subclass reaches `protected` members but not `private` ones (TS2341); a subclass instance
  fits wherever the base type is expected, and reading through the base type hides
  subclass-only members (TS2339) while method calls still run the subclass's version.
- LESSON 44: abstract classes — `abstract class` can't be instantiated (TS2511); `abstract`
  members have no body and every concrete subclass must implement them (TS2654 when several
  are missing, TS2515 for a single one); properties can be abstract too; an implementation
  still has to fit the declared type (TS2416) and can't be reached with `super` (TS2513); an
  abstract class still holds shared state and finished methods, and its name is still a type;
  choose `abstract` over a default implementation when no default would be right.
- LESSON 45: composition vs inheritance (no new syntax) — inheritance is "is a", composition is
  "has a" (the class holds another object as a property and delegates to it); inheritance ties
  a subclass to the base's protected surface, brings everything whether wanted or not, is fixed
  at creation, and a class can extend only one class; composition picks the part when the
  object is built and lets unrelated classes share it; when the only difference is a value,
  neither is needed — a field is enough; either way, ask the part through its public surface
  instead of reaching into its private data.

MISCONCEPTIONS TO WATCH FOR, IN ORDER OF LIKELIHOOD

1. Deleting a property declaration to make TS2564 go away. Ask them what the class's
   properties are after the deletion, and what the compiler says about `this.borrower` then.

2. Writing `paid = 0` instead of `this.paid = 0` inside the constructor. Ask them which
   `paid` that line assigns, and whether the object has changed afterwards.

3. Thinking TS2564 points at the wrong line. Ask them what the message actually claims
   ("never assigned") versus what they expected it to claim ("this assignment is missing").

4. Formatting a number with `toFixed(2)` and believing the stored value changed. Ask them
   what `toFixed` returns, and which value the check compares.

5. Reaching for a class for plain data with no behavior. Ask them which operations belong to
   the data, and what a class adds over the object types from LESSON 16.

6. Changing `private` to `public` to make TS2341 go away. Ask them which rule the class was
   protecting, and who can break it once the property is public.

7. "`private` means nobody can read the value." Ask them what `JSON.stringify` prints, and
   what the compiled JavaScript contains.

8. Checking a rule after changing the data (subtract, then test for a negative balance). Ask
   them what the object holds after a refused operation.

9. Removing `readonly` because a method needs to change the property. Ask them whether that
   data really changes during the object's life, or whether a new object is the honest answer.

10. "`readonly` on an array means the array can't change." Ask them what `push` does, and
    which type they would need to stop it.

11. Writing a constructor parameter without a modifier and expecting a property. Ask them
    what TS2339 says, and which word creates the property.

12. Using `this` for a static member, or making a shared counter an instance property. Ask
    them how many copies of that value should exist, and how many their code creates.

13. Marking a counter `static readonly` and being surprised the constructor is reported. Ask
    them where `readonly` still allows an assignment.

14. Calling a getter with parentheses (`card.available()`), or writing `get` and then reading
    the stored `_value` from outside. Ask them what the getter is called, and what the
    underscore name is for.

15. Storing a derived value in a property and updating it by hand. Ask them what happens the
    first time a method forgets to update it.

16. Naming the stored property and the accessor the same thing. Ask them to read TS2300, then
    ask what `return this.balance` inside `get balance()` would do if it were allowed.

17. Copying the base class's code into an override instead of calling `super.method()`. Ask
    them what has to happen the day the base version changes.

18. Writing `this.method()` inside an override of `method()`. Ask them which function that
    calls, and how many times.

19. Making a base member `protected` (or `public`) just to silence TS2341 in a subclass. Ask
    them whether the subclass really needs that member, or whether the base class already
    exposes what it needs.

20. Expecting a subclass-only method to be callable through the base type. Ask them what the
    other elements of that array are, and what the type promises.

21. Copying shared methods from the abstract class into each subclass. Ask them what has to
    happen when that shared rule changes.

22. Giving an abstract member a default implementation "to be safe". Ask them what a subclass
    that forgets it would do, and whether anyone would notice.

23. "abstract stops the object from being created at runtime." Ask them what the compiled
    JavaScript contains, and which line actually throws.

24. Reaching for a subclass whenever anything differs. Ask them what the two classes would
    really do differently, and whether a field or a held object would say it more simply.

25. Holding a part and then reading its private data (or making it public to do so). Ask them
    which object owns that data, and what it should be asked instead.
