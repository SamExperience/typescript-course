WHAT THEY ARE LEARNING HERE
- LESSON 46: interface syntax — `interface Name { property: type; }` names the shape of an
  object, the same job as the object type aliases of LESSON 24; `?` marks a property that may
  be missing (reading it gives TS18048 until it is checked or defaulted with `??`); `readonly`
  marks one that can be set at creation and never again (TS2540, checked but not enforced at
  runtime); interfaces are structural, so any object of the right shape fits with no keyword on
  the object; object literals get the excess property check (TS2353, TS2561 with a spelling
  suggestion) while the same object assigned through a variable passes; an interface is a type
  only, so using it as a value gives TS2693.
- LESSON 47: method definitions — `method(arg: T): R;` and `method: (arg: T) => R;` declare the
  same thing (the shorthand reads like a class method, the arrow form like a swappable value);
  any object with matching functions fits, including a class instance that never mentions the
  interface; parameter types inside a matching object literal come from the interface
  (contextual typing); a missing method is TS2741, a wrong signature TS2322 with the mismatched
  part underneath, a wrong call TS2554; an optional method (`onFailed?()`) must be checked
  before it is called (TS2722), either with `!== undefined` or with `?.()`. This is the other
  half of LESSON 45: composition holds a part, an interface says what the part must do.
- LESSON 48: `interface B extends A` gives B everything A declares, `readonly` and `?`
  included, and an interface may extend several at once (unlike a class, which has one parent);
  a B value fits wherever an A is expected, and through A only A's properties are visible
  (TS2339) — the LESSON 43 rule without any class; missing inherited properties are reported
  the usual way (TS2739 / TS2741); an extension may narrow an inherited property
  (`amount: 2 | 5 | 10` over `amount: number`) but not contradict it (TS2430); a literal `kind`
  on each extension turns the family into the discriminated union of LESSON 27.
- LESSON 49: `class C implements I` is a check at the class, not inheritance — it brings in
  nothing, and a class with the right shape already fits without it; what it buys is that a
  missing or private member is reported on the class line (TS2420, with "is missing" or "is
  private in type C but not in type I") and a wrong signature as TS2416, the same message an
  incompatible override gets; a getter satisfies a `readonly` property; a class may implement
  several interfaces and extend a class at the same time; an object literal can satisfy an
  interface but not a class type that has private members (TS2739 naming them).
- LESSON 50: choosing between them — for a plain object shape both work and they mix (an
  interface can extend an object type alias, and a class can implement one); only an alias can
  name a union, a literal union, a tuple, a function type or a primitive; two interfaces with
  the same name merge silently while two aliases are reported (TS2300 "Duplicate identifier");
  `implements` reads as a contract with an interface. Rule of thumb: `interface` for object
  shapes other code depends on or classes implement, `type` for unions, tuples, function types
  and local shapes — and consistency inside a project beats the rule.

MISCONCEPTIONS TO WATCH FOR, IN ORDER OF LIKELIHOOD

1. Removing `readonly` to make TS2540 go away. Ask them whether that value really changes
   during the object's life, and which property the code should have been writing to.

2. Marking every property optional so the sample data compiles. Ask them what every reader of
   the interface then has to do, and which properties genuinely may be absent.

3. Reading an optional property without handling `undefined`. Ask them to read TS18048 aloud
   and say which value the message is about.

4. "The extra property is fine, the object has more than enough." Ask them why the same object
   passes through a variable but not as a literal, and what the check is protecting them from.

5. Using an interface name as a value (`typeof Customer`, `new Customer()`). Ask them what is
   left of the interface in the compiled JavaScript.

6. Adding a property that is worked out from other properties. Ask them what happens when the
   underlying data changes and nobody updates it.

7. Branching on `rule.name === "Percent"` inside a function that takes the interface. Ask them
   which object already knows that answer, and what happens when a third rule appears.

8. Calling an optional method without checking. Ask them to read TS2722, then ask which value
   the message is about.

9. Rounding the total but not each individual fee. Ask them what a receipt for one transfer
   would print.

10. Adding a variant-only property as optional on the shared interface to silence TS2339. Ask
    them what that property would mean for the kinds that never have it.

11. Copying the shared properties into every interface instead of extending. Ask them where
    the next shared property would have to be added.

12. Expecting a function that takes the base type to reach variant properties. Ask them which
    check has to happen first, and where it belongs.

13. Deleting `implements` to make TS2416 or TS2420 go away. Ask them where the same mistake
    would be reported instead, and who would find it.

14. "`implements` gives my class the interface's methods." Ask them what the interface
    contains, and what would run if a method were missing.

15. Making a private flag public instead of exposing a getter. Ask them who should be able to
    change it, and who should only read it.

16. "Interfaces are for classes, type aliases are for data." Ask them to write a union as an
    interface, and a class that implements an object type alias.

17. Widening a literal union to make a value fit (adding "GBP" to a currency list). Ask them
    which other code now has to answer for the new value.

18. Declaring the same interface name twice in a project by accident. Ask them what the
    compiler reports, and where the error would show up instead.
