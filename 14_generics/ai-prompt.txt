WHAT THEY ARE LEARNING HERE
- LESSON 51: why generics exist and generic functions — the alternatives all lose something
  (one function per type, `unknown[]` returning `unknown` that the caller can't use, or a union
  that widens the result); `function first<T>(items: T[]): T | undefined` links the argument to
  the result; `T` is usually inferred from the argument and an explicit `<string>` is checked
  like anything else (TS2345); inside the function `T` promises nothing, so any member access
  is reported (TS2339 "does not exist on type 'T'") and returning a non-`T` gives TS2322 with
  "'T' could be instantiated with an arbitrary type which could be unrelated to 'number'";
  `T` flows into callback parameters; reach for a generic when one function serves several
  types and the caller should keep its own type.
- LESSON 52: generic types and interfaces — `type Result<T> = { ok: true; value: T } | { ok:
  false; error: string }` and `interface Page<T> { items: T[] }`; the type argument is part of
  the name, so using the name alone is TS2314 "requires 1 type argument(s)"; annotations state
  the argument while function calls infer it; a generic function type
  (`type Mapper<T, R> = (item: T) => R`); narrowing a generic union works exactly as in
  LESSON 27 (TS2339 for a property of the other branch); one generic shape replaces a row of
  near-identical named types.
- LESSON 53: generic classes — `class Ledger<T>` lets every member use `T`; the argument is
  fixed at `new` (explicitly, or inferred from a constructor argument); the bare name is not a
  type (TS2314 "Generic type 'Ledger<T>' requires 1 type argument(s)") and `Ledger<A>` is
  unrelated to `Ledger<B>` (TS2322); static members cannot mention `T` (TS2302 "Static members
  cannot reference class type parameters"), because a static exists once for every `T`; a
  subclass can fill the argument in (`class NoteLedger extends Ledger<string>`); generic
  classes suit containers, not classes with rules about their content.
- LESSON 54: constraints and `keyof` — `<T extends { amount: number }>` lets the body read what
  the constraint promises while the caller still gets its own type back; a failing argument is
  TS2345 with "Property 'amount' is missing in type ... but required in type ..."; a constraint
  may be an interface; `keyof T` is the union of `T`'s property names and `T[K]` is that
  property's type, so `field(payment, "amount")` is a number and a misspelled key is TS2345
  ("not assignable to parameter of type 'keyof Payment'"); constrain to exactly what the body
  reads, never to the concrete type.
- LESSON 55: practical patterns and avoiding needless generics (no new syntax) — the four
  shapes that cover almost everything (container, result box, transformer `<T, R>`, constrained
  reader); the test for whether a type parameter earns its place is whether it **appears at
  least twice**, since a parameter that appears once links nothing and can be replaced by its
  constraint; one type parameter per job, and more than two is a warning sign; a concrete type
  gives better errors than a `T` that never varies.

MISCONCEPTIONS TO WATCH FOR, IN ORDER OF LIKELIHOOD

1. "`T` is like `any`." Ask them what they can do with a value of type `T` inside the
   function, and what the caller gets back in each case.

2. Using a property or method of `T` inside a generic function. Ask them which types the
   function promises to work for, and whether every one of them has that member.

3. Writing `unknown[]` instead of `T[]`. Ask them what the caller has to do with the result.

4. Making everything generic. Ask them which second type the function will ever be called
   with, and what `Payment[]` tells a reader that `T[]` doesn't.

5. Passing an explicit type argument that fights the value (`lastTwo<string>(payments)`). Ask
   them who decides `T`, and what the argument already says.

6. Writing `Result` without its argument in an annotation. Ask them what TS2314 asks for, and
   what kind of value that particular result carries.

7. Writing one result type per kind of value (AmountResult, AccountResult). Ask them what
   differs between the two declarations.

8. Trying to print or compute with the value inside a generic result. Ask them what the
   function knows about `T`.

9. Making a static member instance-level to get rid of TS2302. Ask them when a static exists,
   and how many different `T`s share it.

10. Giving a class a type parameter it never varies (an account, a schedule). Ask them which
    second type that class will ever hold.

11. Returning the internal array from a container. Ask them what a caller can then do to the
    container's own rules.

12. Constraining to the concrete type (`<T extends Movement>`) instead of the shape the body
    reads. Ask them which other lists would stop working.

13. Returning the constraint instead of `T` (`{ amount: number } | undefined`). Ask them what
    the caller can still read from the result.

14. Reading a property by a plain `string` key. Ask them what happens to a typo, and what
    `keyof T` would have said.

15. Keeping a type parameter that appears once "in case it's useful later". Ask them what it
    links, and what the signature would look like with the constraint in its place.

16. Sorting with `items.sort(...)` inside a helper. Ask them what happened to the caller's
    list.
