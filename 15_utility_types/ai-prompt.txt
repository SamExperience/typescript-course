WHAT THEY ARE LEARNING HERE
- LESSON 56: `Partial<T>` (every property optional — the shape of an update), `Required<T>`
  (every property required, TS2741 for a missing one) and `Readonly<T>` (every property
  readonly, TS2540 on assignment; a promise not to change the caller's object). Each builds a
  new type and leaves the original alone; a `Partial<T>` is not a `T` (TS2345, with "Type
  'string | undefined' is not assignable to type 'string'"); reading a `Partial` property needs
  an `undefined` check (TS18048); all three are shallow, and `Readonly` is a compile-time rule
  only — the assignment really runs if the compiler is not consulted.
- LESSON 57: `Pick<T, K>` keeps the named properties and `Omit<T, K>` removes them, carrying
  over each property's type, `?` and `readonly`; a key that isn't in `T` is reported for `Pick`
  (TS2344 "does not satisfy the constraint 'keyof Account'") but **silently ignored by `Omit`**;
  an object literal with an extra property is TS2353, while a value of the full type fits where
  the smaller type is expected; `Pick` for a deliberate short list, `Omit` for a deliberate
  removal (and `Omit` keeps up when new fields arrive).
- LESSON 58: `Record<K, V>` types an object used as a table; with a literal union of keys a
  missing entry is TS2741 and an unknown one TS2353, so adding a value to the key union reports
  every table that hasn't been updated; `Record<string, V>` accepts any key and types every
  read as `V` even when the key is absent (the runtime value is `undefined`, and
  `noUncheckedIndexedAccess` from LESSON 36 is what changes that); indexing a record with a
  plain `string` (for example from `Object.keys`) is reported.
- LESSON 59: `Exclude<T, U>` removes union members and `Extract<T, U>` keeps them; on a
  discriminated union `Extract<Movement, { kind: "card" }>` names one variant and
  `Exclude<Movement, { kind: "fee" }>` names all the others, so a new variant is picked up
  automatically; a value outside the result is TS2322; removing a member that isn't in the
  union is silently accepted (like `Omit`); an empty `Extract` is `never`, which nothing can be
  assigned to (LESSON 66 explains `never`); `filter` with a short inline callback does narrow its
  result in TS 6.0.3 (the compiler works out the rule itself), but a loop with a narrowing `if`
  is the version that keeps working when the callback grows or its return type is annotated.
- LESSON 60: `ReturnType<F>` and `Parameters<F>` read a function type, and `typeof fn` in a
  **type position** is how you name the type of a function you wrote (the same keyword as the
  runtime `typeof` of LESSON 10, in a different place); `Parameters<F>` is a tuple, so
  `Parameters<typeof fn>[0]` is the first parameter; both require something callable (TS2344
  "does not satisfy the constraint"), and forgetting `typeof` gives TS2749 "refers to a value,
  but is being used as a type here"; derive the type when the function is the source of truth,
  annotate the function when the type is.
- LESSON 61: combining them (no new syntax) — read a nested utility type from the inside out;
  `Partial<Pick<T, K>>` is a patch limited to certain fields (a plain `Partial<T>` would let a
  caller send anything), `Record<K, Omit<V, "secret">>` is a table of trimmed views,
  `Readonly<Record<K, V>>` is a table built once and only read; name the intermediate steps and
  stop nesting at two levels, because the names are what error messages show.

MISCONCEPTIONS TO WATCH FOR, IN ORDER OF LIKELIHOOD

1. "`Partial<Account>` is an `Account` with fewer fields, so I can pass it anywhere." Ask them
   what the compiler says, and which property it names first.

2. Reading a `Partial` property without checking it. Ask them to read TS18048 aloud, then ask
   what `?? current` would do.

3. "`Readonly` freezes the object." Ask them what the compiled JavaScript contains, and what
   happens when the assignment actually runs.

4. Expecting `Readonly` or `Partial` to reach inside a nested array or object. Ask them what
   `push` does to a readonly array property.

5. Reaching for `Required<T>` on stored data whose fields are genuinely sometimes missing. Ask
   them where in the program the gaps are actually filled.

6. Editing the object in place inside an "update" function. Ask them who else holds that
   object.

7. Writing a smaller view out by hand instead of deriving it. Ask them what happens to that
   type the day the original changes.

8. Trusting `Omit` with a misspelled key. Ask them what the resulting type contains, and who
   checks that name.

9. Typing a lookup table as `Record<string, V>` when the keys are known. Ask them what the
   compiler can still report, and what a missing key returns at runtime.

10. Indexing a `Record` with a key from `Object.keys`. Ask them what type those keys have.

11. Writing `Exclude<Entry, "pending">` for a union of object types. Ask them what the members
    of that union actually are.

12. Expecting `filter` to return the narrowed variant type. Ask them what type `filter`
    promises back, whatever the condition says.

13. Listing the remaining variants by hand instead of using `Exclude`. Ask them what happens
    when a fourth variant appears.

14. Writing `ReturnType<fn>` without `typeof`. Ask them to read TS2749, then ask what `fn` is
    at runtime and what a type position expects.

15. Annotating a function's return type AND deriving a type from it. Ask them which of the two
    is the source of truth.

16. Using `Partial<T>` where `Partial<Pick<T, K>>` is meant. Ask them which fields a caller
    could then change.

17. Filling a `Readonly<Record<...>>` field by field after creating it. Ask them what readonly
    promises, and when the table is meant to be complete.

18. Nesting three utility types in one line. Ask them to say the type out loud in one
    sentence.
