WHAT THEY ARE LEARNING HERE
- LESSON 62: `typeof` and `instanceof` — `typeof null` is `"object"`, so that branch narrows to
  `null` and reading anything there is TS18047 ("possibly 'null'"); `instanceof C` narrows to
  instances of a class, and the right-hand side must exist at runtime, so a type alias gives
  TS2693 ("only refers to a type, but is being used as a value here"); before the check only
  the union's shared members are available (TS2339, whose detail names the variant that lacks
  it) and inside it the other variant's members are out of reach; arrays are narrowed with
  `Array.isArray`, not `typeof`; a member both variants share needs no narrowing at all.
- LESSON 63: the `in` operator — `"property" in value` narrows a union of plain object types,
  where `instanceof` can't help, and narrows both branches (present in the `if`, absent in the
  `else`); the property name is **not** checked against the union, so a name no variant has
  compiles, types the property as `unknown` and never matches; an optional property shared by
  several variants is a poor discriminator, but `in` is exactly the right question for "was
  this optional property set at all?"; when you own the types, a shared literal field beats
  both `in` and `instanceof` (LESSON 64).
- LESSON 64: discriminated unions — every variant carries the same field with a different
  **literal** value, and a `switch` on it narrows every branch including `default`; a `case`
  outside the union is reported (TS2678 "is not comparable to type"), which is the check a
  `kind: string` quietly removes; with both variants declared `kind: string` nothing narrows at
  all (TS2339); outside the switch only the shared fields are available; use one field name
  (`kind` or `type`) everywhere, and keep the values short and stable.
- LESSON 65: user-defined type guards — `function f(x: T): x is U` tells every call site what a
  `true` means, so `if (f(x))` narrows and `list.filter(f)` returns `U[]`; TypeScript already
  works this out for a short inline callback, but **not** when the function's return type is
  annotated `: boolean` or the body grows past one expression, which is exactly when the
  `x is U` annotation brings the narrowing back; a guard is also how an `unknown` value becomes
  typed; the compiler **trusts** the annotation, so a guard whose body doesn't prove it is
  accepted in silence and every call site believes it.
- LESSON 66: exhaustive checking and `never` — `never` is the type with no values, so
  `const impossible: never = value` in a `default` branch compiles only while every variant has
  been handled; a new variant is then reported in **every** switch that forgot it (TS2322,
  naming the variant), instead of silently falling into the default; `never` also marks a
  function that never returns normally (TS2534 "A function returning 'never' cannot have a
  reachable end point"), which is not the same as `void`; an empty `Extract` (LESSON 59) is the
  other place they have already met it.

MISCONCEPTIONS TO WATCH FOR, IN ORDER OF LIKELIHOOD

1. Using `typeof value === "object"` to rule out `null`. Ask them what `typeof null` returns,
   and what the value can be inside that branch.

2. `instanceof` on an interface or type alias. Ask them what is left of that name when the code
   runs.

3. Reading a variant-only property before the check. Ask them which members the union
   guarantees.

4. Reading the other variant's property inside a narrowed branch. Ask them what the check just
   proved about the value.

5. Narrowing when both variants share the member. Ask them what each branch would do
   differently.

6. `typeof value === "array"`. Ask them what `typeof []` actually returns.

7. Using `in` on a property that several variants share (often an optional one). Ask them what
   that check proves about which variant they hold.

8. Assuming a misspelled property name in an `in` check would be reported. Ask them what type
   the property has inside that branch, and how often the branch runs.

9. Adding a third shape and expecting the old `in` checks to complain. Ask them which branch
   the new shape falls into.

10. Declaring the discriminant as `kind: string`. Ask them what a typo in a `case` would do
    then, and what the compiler can still check.

11. Reading a variant-only field outside the switch. Ask them which fields every variant
    guarantees.

12. Handling a new variant in one function and forgetting another. Ask them which function
    would say nothing, and what a reader of the statement would see.

13. Annotating a check `: boolean` and expecting `filter` to narrow. Ask them what the boolean
    tells the compiler about the value.

14. Writing a guard whose body checks something weaker than the type it promises. Ask them
    what the compiler checks about that annotation, and where the mistake would surface.

15. Changing the call site (or the array's type) instead of the guard. Ask them which function
    actually knows the answer.

16. Deleting the `never` line to make the error go away. Ask them what the new variant does in
    the default branch once the check is gone.

17. Handling a new variant in one switch and leaving the other. Ask them to read both errors,
    which name the same variant.

18. Confusing `never` with `void` or `undefined`. Ask them which of the three a function that
    always throws returns.
