WHAT THEY ARE LEARNING HERE
- LESSON 71: what a decorator is and its syntax — `@name` above a class member wraps it with an
  ordinary function that runs **once, when the class is defined**; TypeScript 6 uses the
  standard (TC39) model, with no `experimentalDecorators` setting; a method decorator receives
  `(target, context)`, where `context.name` and `context.kind` describe the member, and what it
  returns replaces the member; the generic signature
  `<This, Args extends unknown[], Return>(target, context: ClassMethodDecoratorContext<This, ...>)`
  is what keeps it typed for every method it is applied to, and a signature that is too loose is
  reported at the `@` (TS1241 "Unable to resolve signature of method decorator when called as an
  expression", TS1270 "Decorator function return type ... is not assignable").
- LESSON 72: a practical example — a decorator with options is a **factory** that you call
  (`@rounded(2)`), and forgetting the call makes the factory itself the decorator (TS1241);
  narrowing the `target` type (for example to methods returning a number) means a wrong method
  is reported at the `@`; with two decorators the factories are evaluated top to bottom, the
  decorators are applied bottom-up, and at call time the wrappers run outside in and unwind in
  reverse; anything that depends only on the options is computed once, when the decorator is
  applied.
- LESSON 73: when to use them and when not (no new syntax) — a decorator is a wrapper with
  special syntax, so everything it does a plain higher-order function can do; they earn their
  place for a uniform concern across many members (logging, timing, clamping) and in frameworks
  built around them (Angular, NestJS); they cost invisibility at the call site, definition-time
  behavior, fiddly types and awkward testing; a wrapper function or composition (LESSON 45) is
  usually clearer in your own code; the rule is to use one when not seeing it costs the reader
  nothing — which is also why this course's mini-projects ban them.

MISCONCEPTIONS TO WATCH FOR, IN ORDER OF LIKELIHOOD

1. "A decorator is a type." Ask them what runs, and when.

2. Expecting the decorator to run on every call. Ask them when the class body is evaluated,
   and what the returned function is for.

3. Writing the signature with `unknown[]` parameters. Ask them to read TS1241 and TS1270, then
   ask what the decorator promises about a method taking two numbers.

4. Forgetting to pass the arguments through (`target.call(this)`). Ask them what the wrapped
   method receives.

5. Writing the replacement as an arrow function. Ask them what `this` refers to inside it.

6. Using a decorator factory without calling it (`@clamped` instead of `@clamped(0, 100)`).
   Ask them what the value after the `@` is in each case.

7. Clamping or validating the arguments when the brief is about the result. Ask them which
   value is out of range.

8. Expecting the two stacked decorators to run in the order they are written. Ask them which
   one wraps the method first, and which wrapper is entered first at call time.

9. Reaching for a decorator for a single method, or for a rule that changes what the method
   means. Ask them whether a reader of the call site needs to know it happens.

10. Believing a decorator can do something a function cannot. Ask them to write the same
    behavior as a function that takes a function and returns one.
