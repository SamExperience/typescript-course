WHAT THEY ARE LEARNING HERE
- LESSON 74: conditional types — `T extends U ? X : Y` is an `if` the compiler evaluates while
  checking, and `extends` means "is assignable to", not class inheritance; the usual job is to
  derive one type from another (a format literal deciding which options object is allowed);
  a union handed to a **bare** type parameter **distributes**, so the check runs once per member
  and the results are joined; a branch that produces `never` disappears, because `never` is the
  empty union — which is all `Exclude<T, U> = T extends U ? never : T` is; wrapping both sides
  in brackets (`[T] extends [U]`) compares the union as a whole, and `[T] extends [never]` is
  the only way to ask whether a type is empty; the cost is that inside a generic function `T` is
  still open, so `Options<T>` is all of its branches at once and no property of it can be read
  (TS2339 listing the whole union).
- LESSON 75: mapped types — `{ [K in keyof T]: X }` walks the keys of `T`, and `T[K]` is the
  original value type; **a mapped key keeps the `readonly` and `?` it had** unless the mapping
  changes them, which is why modifiers can be removed with `-readonly` and `-?` as well as
  added; `Partial`, `Readonly`, `Required` and `Record` are all written this way, and the
  source of the keys need not be `keyof T` — any union of keys can be mapped; a mapped type
  earns its place when a derived type has to follow its source, and a hand-written object type
  is plainer for a one-off.
- LESSON 76: `infer` — it names a blank in a pattern and may appear only in the `extends`
  part of a conditional type; `T extends (infer U)[] ? U : never` is "the element type of
  T", and the same trick reaches inside a function type, which is what `ReturnType` and
  `Parameters` are (the standard library writes them with `any` because they must accept
  every function; `(...args: never[]) => infer R` does the same job without it); patterns are
  structural and may hold several blanks, as in `[infer F, ...unknown[]]`; matching is an
  **assignability** question, so `() => infer R` misses a function that takes arguments and
  the false branch — usually `never` — is used silently, until something reads a property of
  that `never`; it pays when it keeps a type in step with the function or shape that produces
  it, and `ReturnType` should be preferred to writing the same pattern again by hand.

- LESSON 77: template literal types — `` `IT${string}` `` describes the shape of a string, and
  a union inside the template **multiplies out**, so two unions of two give four members and
  an error lists all of them (TS2820, with a "Did you mean" suggestion); `Uppercase`,
  `Lowercase`, `Capitalize` and `Uncapitalize` change case; the payoff is the `as` clause of a
  mapped type, which **renames** keys — `` [K in keyof T as `get${Capitalize<K & string>}`] ``,
  where `K & string` is needed because `keyof T` is `string | number | symbol` (TS2344) — and a key renamed
  to `never` is **dropped**, so `as` filters as well as renames; the cost is size, since the
  combinations multiply and every message lists them.

- LESSON 78: combining the four features, and when it becomes too much (no new syntax) — one
  combination worth knowing is
  `` { [K in keyof T as `send${Capitalize<K & string>}`]: (input: T[K]) => string } ``, which is
  a mapped type, a template literal, a case helper and an indexed access in one line; a derived
  type earns its place when the source changes, when there are many members, or when the code
  being described is not yours to edit; write the type out by hand when you cannot say it in
  one sentence, when it does more than one job, when the error would land far from the mistake,
  or when the shape is yours to change; library authors compute types because they cannot edit
  their callers, and an application usually can.

MISCONCEPTIONS TO WATCH FOR, IN ORDER OF LIKELIHOOD

1. Reading `extends` as class inheritance. Ask them whether `"csv" extends string` is about a
   base class, and what would have to be true for the check to pass.

2. Expecting a conditional type to run at runtime. Ask them what is left in the JavaScript
   output.

3. Being surprised that a union gives a union back. Ask them how many times the check runs.

4. Not seeing why the `never` branch vanishes. Ask them how many members `never` adds to a
   union, then ask them to write `Exclude` by hand.

5. Trying to read a property inside a generic function that holds a conditional type. Ask them
   which branch `T` has chosen at that point.

6. Writing the branches in the wrong order, so an earlier branch already matched. Ask them
   which check the value meets first.

7. Reaching for `[T] extends [U]` by habit. Ask them whether the question is about the union as
   a whole or about each member.

8. Using a conditional type where a union or an overload would say the same thing more plainly.
   Ask them to read the type out loud in one sentence.

9. Being surprised that a mapped type kept a `readonly` or a `?` they never wrote. Ask them
   which part of `{ [K in keyof T]: boolean }` talks about modifiers.

10. Writing `?` where `-?` was meant, or the other way round. Ask them whether the goal is to
    allow a field to be missing or to promise it is there.

11. Assuming `Partial<T>` and `{ -readonly [K in keyof T]?: T[K] }` are the same. Ask them to
    assign to a readonly field of each.

12. Building a mapped type for a shape used once. Ask them whether anything would break if the
    source type changed.

13. Writing `infer` outside a conditional type. Ask them where the blank is supposed to be
    filled in from.

14. Expecting a pattern that does not match to be reported where it is written. Ask them what
    the false branch gives, and where that value is first used.

15. Assuming `() => infer R` matches every function. Ask them whether a function of two
    parameters can be called with none.
16. Expecting a template literal type to keep two unions small. Ask them to count the
    combinations.

17. Renaming a key without `Capitalize`, or without `& string`. Ask them what the new key is
    spelled like, and what a key type can be besides a string.

18. Not realizing that an `as` clause can remove a key. Ask them what happens when the new
    name works out to `never`.
19. Deriving a type that has no source to follow. Ask them what it would be derived *from*.

20. Treating "I could compute this type" as a reason to. Ask them who reads the type, and who
    reads the error when it is wrong.
